# Languages, voice typing and read-aloud

This is the contract every part of the app follows. It is the reference for adding a screen, a server message or a language.

Languages: `en` English, `hi` Hindi, `mr` Marathi, `bn` Bengali, `ta` Tamil. Order is always `[en, hi, mr, bn, ta]`.

Machine-drafted translations must be reviewed by native speakers before real users see them. `npm run i18n:export` writes a CSV for reviewers.

## 1. Rule: every visible string goes through `t()`

Nothing user-visible is a bare English literal in a view, toast, attribute, dialog, `document.title`, or server message. The only exceptions are the **English-only allowlist** (section 4) and **user content** (names, notes, listing text typed by people).

The old phrasebook (`PHRASES` plus `translateTree`, which rewrote DOM text nodes) is gone from production. It survives only as the debug checker (section 7).

## 2. Message catalogs

### Frontend UI strings: `frontend/i18n/<namespace>.js`

One file per view or module. Each one owns its namespace prefix:

```js
// frontend/i18n/tech.js
export default {
  'tech.newJob.title': ['New repair job', 'नया मरम्मत काम', 'नवीन दुरुस्ती काम', 'নতুন মেরামতের কাজ', 'புதிய பழுதுபார்ப்பு வேலை'],
  'tech.trust': ['Trust score {n}', 'भरोसा स्कोर {n}', 'विश्वास गुण {n}', 'ভরসা স্কোর {n}', 'நம்பிக்கை மதிப்பெண் {n}'],
  // plural: any element may be an object keyed by Intl.PluralRules category
  'tech.years': [{ one: '{n} year', other: '{n} years' }, '{n} साल', '{n} वर्षे', '{n} বছর', '{n} ஆண்டுகள்'],
};
```

| Namespace file | Owner (the code that uses it) |
|---|---|
| `common.js` | shared words: buttons (Save, Cancel, Yes, No, Back, Close), nav labels, statuses, generic errors, validation messages, units, page titles (`title.*`) |
| `shell.js` | app.js, ui.js, fx.js (command palette), auth.js, api.js, scanner.js, illustrations.js, index.html |
| `speech.js` | speech.js and voice.js: listen bar, mic, rate, audio mode, "no voice" help |
| `landing.js`, `account.js`, `tech.js`, `owner.js`, `passport.js`, `parts.js`, `stock.js`, `collector.js`, `recycler.js`, `brand.js`, `market.js`, `admin.js`, `request.js`, `green.js`, `journey.js` | the view of the same name (`journey.js` is shared by the owner, request and Green Passport pages) |

`frontend/i18n/index.js` imports every namespace file and merges them. A duplicate key across files is an error that `scripts/check-i18n.mjs` reports.

### Server messages and catalog labels: `backend/src/core/messages.js`

These use the same tuple format. They are shared with the browser through `scripts/sync-core.sh`, so `frontend/core/messages.js` is a generated copy.

The file holds:

- error codes (`err.*`)
- notifications (`notif.*`)
- job timeline and passport events (`event.*`)
- SMS (`sms.*`)
- insight rules (`rule.*`)
- field names (`field.*`)
- option text (`opt.*`, `next.*`)
- customer notifications (`cnotif.*`, same title/body shape as `notif.*`, stored under the customer's Green Passport)
- reward reasons (`reward.*`), badges (`badge.*`), match reasons (`match.*`), journey details (`journey.d.*`), contact methods (`contact.*`) and the request consent text (`consent.request`)

It exports `MSG` and `format(key, params, lang)`. Lambdas use `format` for SMS in the owner's language.

**Catalog labels** in `backend/src/core/catalog.js` are objects with all five languages: `{ en, hi, mr, bn, ta }`. This covers categories, components, causes, severity, spare, barriers, gates and area names (`AREAS[x].name` becomes `{ en, hi, mr, bn, ta }`).

## 3. The i18n API: `frontend/js/i18n.js`

```js
import { t, L, lang, setLang, LANGS, fmt, en, user, renderMsg, errorText, onLangChange, localeOf } from './i18n.js';
```

- `t(key, params?)` returns the string in the current language, with `{name}` placeholders filled in.
  - Falls back to English, then to the key itself.
  - A missing key logs a `console.warn` once (in debug mode it also outlines the element).
  - Params are substituted as text. Callers still `esc()` the result before putting it in HTML.
  - Plurals: when the tuple element is an object, `params.n` is passed to `Intl.PluralRules(locale)`.
- `L(obj)` takes a catalog label object `{en, hi, mr, bn, ta}` and returns the current language, falling back to `en`.
- `both(obj)` is for technician shop screens. It returns the local name plus the English name, as `<span lang="..">`.
- `fmt` is a set of number and date formatters. They always use Latin digits (`-u-nu-latn`), so amounts and dates match across a screen:
  - `fmt.money(n)` gives `₹3,200`
  - `fmt.kg(n)`
  - `fmt.int(n)`
  - `fmt.date(iso)` and `fmt.dateTime(iso)`, with month names in the current language
  - `fmt.speakMoney(n)` returns "3,200 रुपये" for speech
- `en(str)` returns `<bdi lang="en" data-en>str</bdi>`, the English-only allowlist marker.
- `user(str, langCode?)` returns `<bdi data-user lang="..">esc(str)</bdi>`, the marker for people's typed content.
- `renderMsg(item)` takes a stored server message `{ key, params, text }` and returns a translated string.
  - It returns `t(item.key, resolveParams(item.params))` when the key exists, otherwise `item.text` (old rows).
  - Params may hold typed references that get translated:

    | Reference | Resolves to |
    |---|---|
    | `{ cat: 'washing_machine' }` | category name |
    | `{ comp: ['washing_machine', 'control_board'] }` | component name |
    | `{ cause: id }` | cause |
    | `{ sev: id }` | severity |
    | `{ spare: id }` | spare-part availability |
    | `{ barrier: id }` | repair barrier |
    | `{ gate: id }` | safety gate |
    | `{ area: '110' }` | area name |
    | `{ opt: id }` | option name (`opt.<id>`) |
    | `{ status: s }` | status label |
    | `{ msg: key, params }` | nested message |
    | `{ money: n }` | formatted amount |
    | `{ kg: n }` | formatted weight |
    | `{ date: iso }` | formatted date |

    Plain strings and numbers pass through unchanged. These are IDs, names and model numbers, which stay as they are.
- `errorText(err)` returns the text for a toast. It is `t('err.' + err.code, resolveParams(err.params))` when the code is known, otherwise `err.message`.
- `tIn(lang, key, params)` and `withLang(lang, fn)` produce text in another language, for example the owner's WhatsApp message, the bill, and printed QR tags.
- `setLang(code)` is async. It saves the choice (guarded with try/catch), sets `<html lang>`, and notifies the `onLangChange` subscribers.
- Language on first visit, in order:
  1. `?lang=xx` in the query string, before the `#` (owner links carry it)
  2. the saved choice
  3. `navigator.languages`
  4. `en`

### Server error shape

Core code throws `apiError(status, code, params)` (`backend/src/core/util.js`). It builds the English message from `err.<code>` and calls `httpError(status, message, code, params)` (`catalog.js`). `handle()` returns `{ error: englishMessage, code, params }`. A database error with no status becomes code `conflict`.

- `frontend/js/api.js` copies `code` and `params` onto the thrown `Error`.
- `toast()` and `errorText()` show the translated version.
- Tests assert on `code`.

### Stored messages

Each keeps an English fallback for logs and old rows:

- timeline and passport events: `{ key, params, text }`, rendered with `renderMsg(e)`
- notifications: `{ key, params, title, body }`, rendered with `renderMsg(n, 'title')` and `renderMsg(n, 'body')` (keys `<key>.title` and `<key>.body`)
- insight recommendations: `renderMsg(r, 'action')` and `renderMsg(r, 'why')`
- alerts and pickup items: `renderMsg(x)`, falling back to `message` or `label`

## 4. English-only allowlist

Mark these with `en()` or `data-en`. Anything else in Latin script is a bug.

- the brand name `Punarnava` (the wordmark, and `पुनर्नवा` beside it)
- product brand and model identifiers (`Brand X`, `WM-7`)
- every ID: job, passport (pid), part, pickup and listing IDs, and QR payloads
- recycler or CPCB registration numbers, and phone numbers
- `₹` and unit symbols inside formatted numbers (`kg`)
- legal fine print in the footer (the fictional brands notice and the Environmental Hacks credit), and the demo-mode banner
- the CSV export in brand.js, which is English plus codes because it is meant for analysts
- the brand PDF report (`backend/src/core/report.js`, `pdf.js`): the standard PDF fonts are Latin-only and Indian scripts would need embedded fonts and text shaping. The download button, dialog and messages around it are translated, and the on-screen report and Print view follow the app language
- developer and ops errors that never reach a normal user (`No route…`) and SNS ops alerts

The words *around* these values are still translated, for example "Job {id} is ready".

## 5. Language of people's content

- A job stores `ownerLang`. The technician picks it on the new-job form, defaulting to the technician's own UI language. The owner page updates it when the owner changes language.
- Owner links put the language in the query string before the hash: `${APP_URL}/?lang=<ownerLang>#/o/<jobId>/<token>`. After the hash it would be read as part of the token.
- WhatsApp, SMS and bill text that goes to the owner uses `ownerLang`.
- A technician note stores `noteLang` and is rendered with `user(note, noteLang)`. That way read-aloud uses the right voice.

## 6. Speech: `frontend/js/speech.js`

Speech works in the browser first, with AWS as the fallback. `voice.js` stays as a compatibility layer that re-exports from speech.js.

### Capabilities

`capabilities(lang)` returns `{ tts: 'browser'|'cloud'|'none', stt: 'browser'|'cloud'|'none', record }`. The result is probed once per language and cached.

### Text to speech

```js
speak(items, { lang, onItem, onDone })   // items: [{ text, el? }] → Promise<{ ok, engine }>
stop()
getRate() / setRate(0.75 | 1 | 1.25)
readElement(el)
readMain()
```

- `readElement(el)` reads the visible text of `el` in DOM order:
  - It honours `data-say` overrides.
  - It skips `[aria-hidden]`, `[data-no-read]` and `.sr-only`.
  - `bdi[data-user][lang]` is spoken with that language's voice when one exists.
- `readMain()` reads `#main`.

Fallback order:

1. The browser voice for the exact language.
2. Cloud TTS: `POST /public/tts` or `POST /api/tts` with `{ text, lang }`, which returns `{ url }` (a presigned S3 mp3) or `{ unsupported: true }`. Amazon Polly has voices only for `en` (en-IN) and `hi` (hi-IN).
3. For `mr`, `bn` and `ta` with no device voice: a translated help panel ("Install the Marathi voice: Settings → Text-to-speech → Google → Install voice data"). If the language is `mr`, the panel offers an explicit opt-in to "use the Hindi voice". The app never switches voices silently.

Long text is split into sentence chunks of about 180 characters. Each utterance has a watchdog, so a missing `onend` cannot stall reading (Chrome Android).

### Speech to text

```js
listen({ lang, mode: 'text'|'digits'|'choice', choices }) // → { stop(), done: Promise<{ text, alternatives, engine }> }
```

Fallback order:

1. Browser `SpeechRecognition`, probed by actually running it. If it errors with `language-not-supported`, `service-not-allowed` or `network`, it falls through.
2. Cloud STT, but only for signed-in users and owner links:
   1. MediaRecorder captures up to 15 s.
   2. The clip is uploaded through a presigned upload: `POST /api/stt/uploads` when signed in, `POST /public/owner/:jobId/uploads?t=` on an owner link. Both put it under `uploads/tmp/`, where it is deleted once read (and by a 1-day bucket rule). Voice notes still use `POST /api/uploads` and are kept.
   3. `POST /api/stt` (or `POST /public/owner/:jobId/stt?t=`) with `{ key, lang }` returns `{ jobName }`.
   4. The browser polls `GET /api/stt/:jobName` (or the owner equivalent) for `{ status, text }`.
   5. Amazon Transcribe batch handles all five languages in ap-south-1.

### Availability and permissions

- `voiceTypingStatus(lang)` returns `{ ok, key, engine }`; `voiceTypingNote(lang)` renders the translated reason when voice typing cannot work (`speech.err.insecure` on http:// pages, `speech.err.unsupported`, or `speech.err.langListen` once the browser refused that language), followed by "You can still type".
- On an insecure page no mic buttons are added. A microphone the Permissions API reports as denied fails at once with `speech.err.micBlocked`.
- `speechSynthesis` is resumed if paused, and the first utterance waits ~160 ms after a `cancel()` (Chrome drops utterances queued right after one). A language change stops reading and listening.
- Tested in Node with fake browser environments: `backend/test/speech-env.test.js`.

### Voice typing

`enhanceVoiceInputs(root)` adds a mic button to every `input` of type text, search, tel or number (or with no type), and to every `textarea`. It skips readonly, disabled, `[data-novoice]`, password, email and file inputs.

- `data-voice-lang="en"` makes a field listen in English. Model numbers, serials, registration numbers and QR input use it.
- Number and tel fields use `digits` mode. Devanagari, Bengali and Tamil digits are normalised to ASCII.

### Low-literacy features

Every screen gets:

- **A Listen button** in the top bar, which reads the main content. While it reads it shows Stop, and a rate control (slow, normal, fast).
- **Audio mode**, a toggle saved per device. When it is on, every new screen is read automatically, toasts and errors are spoken, and a speaker icon appears on each card. Tapping that icon reads the card. A plain tap on the card still does what it always did.
- **A language picker you can hear.** Each language option carries `lang=` and a speaker button that says the language's name in its own voice.
- **One `aria-live` region** that announces "Listening…", "Processing…" and errors.
- **Error toasts that stay** until dismissed in Audio mode, using `role="alert"`.

## 7. Checks

- `node scripts/check-i18n.mjs` (also run by `npm test` and by `deploy-frontend.sh`). It checks that:
  - every key has five non-empty values
  - the `{placeholder}` sets match across languages
  - no key is duplicated
  - every literal `t('…')` and `format('…')` key exists
  - a static scan of `frontend/js` finds no English letters in `>text<` fragments, `toast('…')`, `confirm/alert/prompt` calls, or `placeholder`/`aria-label`/`title`/`alt` literals that are not wrapped in `t()`, `en()` or `data-en`
- Runtime debug: open with `?i18n-debug=1`. A MutationObserver outlines in red, and logs, any Latin-script text node or attribute in a non-English language that is outside `[data-en]` or `[data-user]`.
- The browser sweep (`node scripts/i18n-sweep.mjs [--langs hi,ta] [--json out.json] [--strict] [--only '#/o/']`) uses headless Chrome over CDP at 360px. It makes demo jobs in each state through the API, then loads every route each persona can reach (plus a few in-page states) in all five languages with `?i18n-debug=1`, and prints flagged text, missing keys, console errors and sideways scrolling, plus a speech check (Listen control, Audio-mode speaker buttons, mic buttons, the no-voice path). It exits 1 on a console error or a route that never renders; with `--strict` also on any flagged text or overflow.
